阶段四：RMDB 代码精读（第 17~21 天）

阶段四：RMDB 代码精读（第 17~21 天）

来源：数据库内核学习路线 阶段四
目标：从"能读代码"到"读得懂全项目"。顺序 = 依赖顺序，从下往上读。
方法：每个文件读完后用自己的话写 3~5 行摘要，存到 docs/reading-notes.md
前置：阶段三-数据库理论（理论已经讲过，现在看实现）

一、总览：六层阅读路线

阅读铁律：先看 .h 的类成员和函数声明，猜职责 → 再看 .cpp 实现 → 用 gdb 打断点跟一遍关键流程 → 写 3~5 行摘要。每天 3 个文件。

二、第 1 层：公共基础（第 17 天上午）

2.1 src/defs.h（72 行，最先读）

定位：全项目最小公分母——行地址、列类型、扫描接口。

看什么 在哪 注意
read_unaligned<T> :17 模板 + memcpy 安全读内存（阶段一讲过）
Rid :39 行地址 = 页号 + 槽号；friend operator==
ColType :50 TYPE_INT / TYPE_FLOAT / TYPE_STRING
coltype2str :54 map 做枚举→字符串
RecScan :63 抽象扫描接口：next/is_end/rid 三个纯虚函数

读法：这个文件应该 10 分钟内读完，读不完说明阶段一没过关，回去补。

2.2 src/common/common.h（92 行）

定位：SQL 结构的内存表示——列、值、条件、SET 子句。

看什么 在哪 注意
TabCol :22 表名+列名；operator< 用 make_pair 比较
Value :31 union 存 int/float + string + shared_ptr<RmRecord> raw
init_raw :56 把 Value 编码进字节缓冲（*(int*)(raw->data) = int_val）
CompOp :75 比较运算符（OP_ADD/OP_SUB 是相对更新用的）
Condition :77 WHERE 子句：左列 + 运算符 + 右值/右列
SetClause :85 SET 子句；relative 字段 = 相对更新（TPC-C 余额累加，决赛重点）

读法：每个结构体回答三个问题：① 对应 SQL 的哪个语法？② 为什么这么设计？③ 序列化到字节时怎么变？（init_raw 就是答案）

2.3 src/common/context.h

定位：贯穿全链路的"执行上下文"——一个 Context 对象装着执行时需要的所有东西（事务、锁管理器、缓冲池指针等），从入口一路传到最底层的 get_record。

读法：看它有哪些成员字段（都是指针/引用），理解"上下文对象"这种设计模式——以后你写新执行器也要用它。

三、第 2 层：存储（第 17 天下午 ~ 第 18 天）

3.1 src/storage/page.h（93 行）

定位：页的定义。已经精读过，要点回顾：

  • PageId{fd, page_no}：文件描述符 + 页号，唯一标识一页
  • Page：data_[PAGE_SIZE]（4KB 原始字节）+ pin_count_ + is_dirty_ + 前 4 字节 LSN
  • OFFSET_LSN = 0、OFFSET_PAGE_HDR = 4：页头 4 字节留给日志 LSN（恢复用）

读法：注意 friend class BufferPoolManager——只有缓冲池能碰 Page 的私有成员，这是封装。

3.2 src/storage/disk_manager.cpp

定位：文件 I/O 封装。看函数签名即可：

  • open_file(path) / close_file(fd) / get_file_name(fd)
  • read_page / write_page（内部 pread/pwrite）
  • allocate_page(fd)（文件末尾分配新页）
  • fd2pageno_：文件→起始页号映射

读法：不用细读实现，知道"数据库文件 = 一页一页连续存放"就行。重点理解为什么用 pread/pwrite（阶段三讲过：线程安全，自带偏移）。

3.3 src/storage/buffer_pool_manager.cpp（292 行，重点）

定位：缓冲池核心。阶段二精读过并发部分，现在看全貌。

函数 干什么 重点
fetch_page 取一页（在内存直接返回，不在则加载） 加载流程：找 victim → 写回脏页 → 读盘 → 更新页表
new_page 分配新页 锁外 I/O（第 167~220 行）：锁内拷贝旧页数据 → 锁外写盘 → 锁内收尾
unpin_page 用完归还 loading_done_.wait 等加载完成（第 124~125 行）
flush_page 强制写盘 顺带刷日志（page_lsn > persist_lsn 时先 flush log）

读法：画出 fetch_page 的完整状态机（缺页→淘汰→写回→读入→返回）。注意所有 I/O 都在锁外，这是性能红线，决赛优化不要破坏它。

3.4 src/replacer/lru_replacer.cpp

定位：LRU 替换算法。

读法：数据结构是什么（双向链表 + 哈希表？还是 list + 迭代器 map？）——unpin 要 O(1) 找到链表中的节点移除，看它怎么做到。这是阶段五练习 1 的改造对象。

四、第 3 层：记录与索引（第 18 天下午 ~ 第 19 天）

4.1 src/record/rm_file_handle.cpp

定位：表文件管理器——"行"的世界。

读法：跟着 insert_record 走一遍：

  1. 找空闲页（沿 first_free_page_no 链表）
  2. 在页 bitmap 里找空槽
  3. 写数据 + 更新页头
  4. 满页从空闲链表摘除
  5. 注意 context 参数——贯穿到事务管理器和日志（每步都可能要记 WAL、做 MVCC 检查）

4.2 src/record/rm_scan.cpp

定位：全表扫描器。

读法：内部就是"页内槽位遍历 + 跨页"。注意 bitmap 里被删除的槽怎么跳过。这是 SeqScanExecutor 的地基。

4.3 src/index/ix_index_handle.cpp（B+ 树，重点）

定位：B+ 树索引。阶段三讲过理论，现在看实现。

读法（这是全项目算法最密集的文件，分三天消化）：

  1. 先只读 IxNodeHandle：节点的内存布局（键和值怎么排布）
  2. 再读 insert_entry 的分裂逻辑：什么时候分裂、怎么分、父节点怎么更新
  3. 最后读 delete_entry 的合并/借位逻辑（可以略读，决赛很少删）
  4. 全程注意 WriterPreferredSharedMutex 在哪里加锁——为什么分裂时要独占？

4.4 src/index/ix_scan.cpp

定位：索引范围扫描。

读法：iid_（当前节点位置）和 end_（终点）怎么推进——叶子节点之间怎么跳（顺着叶子链表）。这就是"范围查询快"的代码实现。

函数 行号 作用 已掌握？
CanUsePhysicalRecord :597 快路径：没人写+没新提交 → 物理记录可用 阶段二 ✅
CheckWriteConflict :604 写写冲突检测 阶段二 ✅
WaitWriteTurn :620 等写权（200ms 超时） 阶段二 ✅
ReleaseTxnWriter :660 释放写权 + notify_all 阶段二 ✅
TryAppendWriteRecord :690 写之前的总入口（冲突检查 + 登记） 现在读
RecordRead :707 记录读了哪行（SSI 用） 现在读
GetVisibleRecord :879 可见性判断（五步） 阶段二 ✅
GetVisibleDeletedRecords :950 找"我眼里被删的行"（Delivery 用） 现在读
AddRwEdgeAndCheckDangerous :223 SSI 加边 + 危险结构检查 阶段三 ✅

读法：按上表从上往下读一遍（大部分已会），重点补 TryAppendWriteRecord（写操作的总入口）和 PruneCommittedHistory（内存管理，为什么必须剪？——写历史无限增长会内存爆炸）。

5.2 src/transaction/transaction.h（163 行）

定位：事务对象。阶段三讲过，要点：write_set_（写集合）、undo_logs_（撤销日志）、read_ts_/commit_ts_（原子）、prev_lsn_/has_begin_logged_（WAL 链）、latch_（保护 write_set_）。

读法：回答一个问题——为什么 write_set_ 要加锁，而 read_ts_/commit_ts_ 用 atomic？（答：write_set_ 是复合结构，多个字段要一致；单个时间戳一条原子指令就够。阶段二的知识现在用上了。）

5.3 src/recovery/log_manager.cpp

定位：WAL 日志写入。

看什么 说明
LogType 枚举 UPDATE/INSERT/DELETE/BEGIN/COMMIT/ABORT/CHECKPOINT
LogRecord lsn_、log_tot_len_、log_tid_、prev_lsn_（事务日志链）
各子类 InsertLogRecord 带插入的行、DeleteLogRecord 带旧值…
追加 + 刷盘 什么时候 append、什么时候 fsync（commit 前必须刷）

读法：找"commit 时先写日志再干嘛"的顺序——这就是 WAL 原则的代码实现。配合 buffer_pool_manager 的 flush_page 看 LSN 怎么联动。

5.4 src/recovery/log_recovery.cpp

定位：崩溃恢复（ARIES 三阶段）。

函数 行号 作用

读法：顺着 redo 走一遍（第 383 行），看它怎么用 analyze 的结果；再走 undo（第 395 行），看怎么用 prev_lsn_ 链。阶段六的"90 秒恢复"目标就靠优化这里。

定位：执行器基类（阶段一、三都讲过）。复习 Next() 纯虚函数 + get_col 的 find_if lambda。

6.2 src/execution/executor_seq_scan.h（重点）

八、精读方法（每天照做）

  1. 先看头文件：读类的成员和函数声明，先猜"这个类负责什么"
  2. 再看 .cpp：对照阶段三的架构图，看实现和猜测差多少
  3. gdb 跟一遍：打断点走关键流程（比如 insert_record）
  1. 写摘要：每文件 3~5 行中文，追加到 docs/reading-notes.md，格式：

摘要是你决赛冲刺的复习材料，写的时候用"给明天的自己看"的标准。

九、自测清单（带答案）

1. 画出"一条 INSERT 语句从网络到磁盘的完整调用链" ✅

2. 画出"一个事务 commit 时发生了什么" ✅

注意顺序：先发布时间戳再释放写者（让等待者醒来后能看到最新时间戳，做出正确的冲突判断）。

3. 解释 32 客户端并发插入同一张表为什么可能冲突 ✅

答（四个层面，从微观到宏观）：

  1. 页级：所有插入都要往同一个表文件的页里写，同一页的 bitmap/页头要抢 record_latch_ / 缓冲池 latch_
  2. 缓冲池级：页不在内存时多个线程抢同一帧（loading_pages_ 去重）；页淘汰时互相挤占
  3. 索引级：插入要往同一个 B+ 树写，节点分裂时抢 WriterPreferredSharedMutex
  4. 事务级：SI 下如果两个事务插到了相同主键/唯一索引（或相对更新同一行），触发写写冲突 → 后者 ABORT

所以"并发插入同一张表"看似无害，实际每层都有竞争点——这就是为什么决赛要用 32 客户端压测验证稳定性。
