一、先建立直觉：并发是什么？

1.1 一个生活比喻

想象你和一个室友共用一台冰箱。冰箱门上贴着一张纸，记录"牛奶还剩几盒"。

  • 你看到纸上写 1 盒
  • 你拿了一盒，准备把数字改成 0
  • 就在这时，室友也来看纸，看到 1 盒，也拿走一盒，也准备改成 0
  • 结果：两人都拿了一盒，但纸上写的是 0——纸上记录错了，实际还剩 -1 盒

这就是并发问题。两个人在"同一时间"操作同一个东西，结果和"按顺序一个个来"不一样。

数据库就是那台冰箱：32 个客户端同时操作同一批数据，如果处理不好，就会出现"两个人看到同一个余额、各自扣了钱，但账目只扣了一次"这种灾难。

1.2 数据库为什么必须处理并发

  • 单线程数据库：永远安全，但太慢（一个客户端查询时，其他 31 个全排队）
  • 多线程数据库：快，但必须保证并发结果 = 某个串行顺序的结果

决赛的 TPC-C 测试就是 32 个客户端同时猛打你的数据库。并发处理不好 = 数据错乱 = 测试挂掉。

1.3 进程 vs 线程（一句话区别）

进程 线程
是什么 一个运行中的程序 程序里的一条执行线
内存 各自独立，互不共享 共享同一块内存
沟通 要专门机制（IPC） 直接读写同一个变量
比喻 两间独立的房子 同一间房子里的两个人

数据库里用的是线程：同一个进程里开一堆线程，每个线程服务一个客户端连接。因为共享内存，才需要锁。

1.4 并发 vs 并行

  • 并行（parallel）：真的同时干（多核 CPU，两个核各干各的）
  • 并发（concurrent）：看起来同时干（一个核上快速切换，你干一秒我干一秒）

你不需要区分得很细，只需要知道：无论并行还是并发，都有"交叉执行"的可能，都需要锁保护。

二、核心概念（必须刻进脑子）

2.1 竞态条件（Race Condition）

定义：多个线程访问同一个数据，且至少有一个在写，结果取决于执行顺序的"运气"。

经典例子（计数器）：

这就是丢失更新（lost update）。数据库里的经典事故：两个事务同时把余额 100 改成 90，最后余额是 90 而不是 80。

2.2 数据竞争 = 未定义行为（UB）

重点中的重点：在 C++ 里，两个线程同时读写同一个非原子变量（且至少一个在写），是未定义行为（UB，Undefined Behavior）。

UB 是什么意思？编译器可以随便编译，什么离谱结果都可能发生：

  • 值不对（最常见）
  • 程序崩溃 SIGSEGV（你之前遇到的就是这个）
  • 卡死
  • 数据悄悄损坏，几小时后才爆发
  • 甚至"看起来正常"（最可怕，因为你不知道什么时候坏）

记住：C++ 不会帮你检查数据竞争。你写错了，它可能正常运行 1000 次，第 1001 次崩溃。所以必须靠锁和原子操作（下文）来避免。

2.3 临界区（Critical Section）

定义：一段"一次只允许一个线程进入"的代码区域。

比喻：厕所。一次只能进一个人，其他人门口排队。门上要有锁。

2.4 原子操作（Atomic Operation）

定义：不可分割的操作。要么完整执行完，要么完全没执行，中间不会被其他线程插一脚。

counter++ 不是原子的（三步）。但 std::atomic<int> 的 fetch_add 是原子的（硬件保证，CPU 指令级别）。

所有并发问题的解决思路就两条：

  1. 互斥：用锁把临界区串行化（一次一个人进厕所）
  2. 原子：用 atomic 让单个操作不可分割（比如计数器直接用原子指令）

三、工具一：std::mutex 互斥锁

3.1 是什么

std::mutex（mutual exclusion，互斥）是最基础的锁。同一时刻只有一个线程能持有它。

比喻：一把钥匙。谁拿到钥匙谁进房间，其他人等在门外。

问题：如果 counter++ 中间抛异常，unlock() 永远不会执行 → 锁永远不释放 → 其他线程永久卡死。

3.2 lock_guard（RAII 自动解锁）

这就是 RAII（Resource Acquisition Is Initialization）：资源（锁）的获取和释放绑定在对象的构造和析构上。lock_guard 一离开作用域（哪怕因为异常），析构函数自动解锁。永远用 lock_guard，永远不要裸调 lock/unlock。

3.3 unique_lock（可手动控制的 lock_guard）

std::unique_lock<std::mutex> 是 lock_guard 的"加强版"，除了自动解锁，还支持：

  • lock.unlock() 手动提前解锁
  • lock.lock() 再次加锁
  • 配合条件变量（后面第 5 节，这是它存在的最大理由）

为什么重要：数据库里，锁应该只保护内存操作，不该包住磁盘 I/O（I/O 很慢，锁着它 = 所有线程排队等磁盘，性能灾难）。unique_lock 让你能在临界区中间"放行"。

四、工具二：std::shared_mutex 读写锁

4.1 问题：普通 mutex 太粗暴

数据库里 90% 的操作是读，10% 是写。用普通 mutex：读和读之间也互相排斥——两个读者明明不会破坏数据，却要排队，浪费。

4.2 shared_mutex 的规则

  • 读锁（shared）：多个读者可以同时持有（大家一起看，互不干扰）
  • 写锁（unique）：只能一个写者持有，且写的时候没有任何读者（一个人独占改）

比喻：图书馆。很多人可以同时看书（读锁共存）；但图书管理员整理书架时，所有人都得出去（写锁独占）。

注意：std::shared_lock 是读锁（RAII），std::unique_lock 在这里是写锁（RAII）。名字容易混，记：shared = 共享读，unique = 独占写。

五、工具三：std::condition_variable 条件变量

5.1 是什么

让线程等待某个条件成立，而不是傻乎乎地轮询（死循环检查）。

比喻：餐厅等位。两种方式：

  • 差的方式：每 5 秒问一次服务员"有空位吗？"（轮询，浪费 CPU，还慢）
  • 好的方式：拿个等位器，有空位时服务员主动通知你（条件变量）

counter++ 是三步（load → add → store），会被交叉执行。加锁能解决，但锁太重（要进入内核睡眠/唤醒，可能几百纳秒）。

这种"先看再改"要用 compare_exchange（CAS）或加锁。目前你只需要会用 load/store/fetch_add/fetch_sub。

6.3 memory_order：最难的部分，通俗版

问题：CPU 和编译器会重排指令（为了性能）。单线程没问题，多线程时重排可能让别的线程看到"乱序"的副作用。

memory_order 就是告诉编译器/CPU：这里不许乱排。

仓库里只用了三种，够用了：

顺序 通俗含义 仓库用法
memory_order_relaxed 最宽松，只保证这个操作本身原子，不约束顺序 计数器增减、统计（history_prune_epoch）
memory_order_release 发布：我写这个值之前的所有写入，别人 acquire 读到这个值后都能看到 store(commit_ts, release)
memory_order_acquire 订阅：我读到这个值之后，发布者 release 之前写的所有东西对我可见 load(acquire)

核心思想：release/acquire 是一对。release 的人说"我先把东西摆好，再贴出告示"；acquire 的人说"我看到告示，就知道东西已经摆好了"。

比喻：发朋友圈。

  • release = 你先认真写好长文（所有内存写入），然后点发布（store）
  • acquire = 别人刷到你的朋友圈（load），就保证能看到你写的全文

6.5 自测必考：为什么 unordered_map 不能无锁并发读

路线图自测题。答案（三个层次）：

  1. rehash 问题：unordered_map 插入太多元素时会扩容（rehash）——重新分配所有桶，旧桶数组被释放。此时另一个线程正在遍历旧桶 → 悬垂指针 → 崩溃/UB。
  2. 结构不变量：读操作（find）内部要遍历桶链表，而写操作（insert/erase）会改链表指针。读写同时进行，读者可能走到一半指针被改，读到垃圾或死循环。
  3. 原子性缺失：find 不是一个原子操作，它内部是"算哈希 → 找桶 → 走链表 → 比较"多步，任何一步都可能被写操作打断。

结论：标准库容器都不是线程安全的，要么加锁（本项目做法：txn_map_latch_），要么用并发专用容器（如 concurrent_unordered_map，本项目没用）。

七、死锁与锁顺序

7.1 死锁是什么

定义：两个（或多个）线程互相等对方手里的锁，谁都不让，全部卡死。

经典场景（互相等）：

A 拿着 a 等 b，B 拿着 b 等 a → 永远等下去 → 程序假死（CPU 100% 但什么都不干）。

7.2 死锁的四个必要条件（记个口诀：互持不环）

  1. 互斥：锁一次只能一个人拿（mutex 天然满足）
  2. 持有并等待：拿着 a 不松手，又去等 b
  3. 不可剥夺：别人拿着的锁，你不能抢
  4. 循环等待：A 等 B，B 等 A（形成环）

打破任意一个就不会死锁。工程上最常用的是打破"循环等待"——全项目统一锁顺序。

7.3 仓库实例：按固定顺序拿锁

sm_manager.cpp:152-164，lock_index_cache_shards（一次要锁一个表的多个索引分片锁）：

为什么排序？ 假设两个事务都要操作"索引 A 和索引 B"：

  • 事务 1 按"先 A 后 B"拿锁
  • 事务 2 按"先 B 后 A"拿锁
  • 事务 1 拿到 A 等 B，事务 2 拿到 B 等 A → 死锁

排序后，所有人都按 min(id) 先拿 → 拿锁顺序全局一致 → 循环等待不可能出现 → 死锁不可能发生。

这是全项目的铁律：涉及多把锁时，永远按固定顺序（比如先小 ID 后大 ID，先 map_lock 后 history_lock）拿。

  • 查 GetActiveWriter(key)（读对应分片，持片锁）
  • 如果写者就是我自己 → 当作没人写（我能看到自己的修改）
  • 如果是别人在写 → 去翻那个人的 write_set（要拿 txn_map_latch_ 找到他 + 他的 write_set_latch_），从后往前找他对这行的最新写入，取出旧版本（old_version）：
    • 他写的是 INSERT → 旧版本是空的 → 这行对我不可见（返回 nullptr）
    • 他写的是 UPDATE → 旧版本就是写之前的样子 → 我该看到的就是它
  • 这保证了：我没看到别人的未提交修改（别人正在写的行，我看他的旧值）

第 4 步（第 929~931 行）：快路径——newest_committed_write_ts_（acquire 读）≤ 我的 start_ts → 我启动后没人提交过 → 物理记录就是对的，直接返回。

第 5 步（第 932~940 行）：慢路径——我启动后有人提交过写入。查这个 key 的最新写时间戳：

  • 没有写过 / 最新写 ≤ 我的 start_ts → 物理记录仍然正确，返回
  • 最新写 > 我的 start_ts → 说明这个 key 在我启动后被改过，物理记录是"新版本"，我不能看 → 调用 RewindShardedHistory 倒带：沿着写历史从新到旧找，跳过所有 commit_ts > 我的 start_ts 的写入，找到第一个 ≤ start_ts 的版本
  • 倒带结果 size == 0 → 说明在我启动时这行还不存在/已被删 → 返回 nullptr（不可见）

一句话总结：“先看有没有人正在写（看他的旧值），再看有没有人提交过（沿着历史倒带），都没有就用物理记录”。

练习 4：用 TSAN 抓一个故意写错的并发程序

TSAN（ThreadSanitizer）能自动检测数据竞争，是阶段二最重要的调试武器。

用法要点：

  • 报告会指出哪一行读写冲突，以及两个线程各自的调用栈
  • TSAN 需要重编译，跑起来比正常慢 5~10 倍，但抓竞态极准

十二、自测清单（带答案）

1. 能解释 GetVisibleRecord（transaction_manager.cpp:879）的可见性逻辑 ✅

答（五步，见 8.2 节）：

  1. 物理记录为空 → 不可见
  2. 非 MVCC 事务 → 直接看物理记录
  3. 有人正在写这行（且不是我）→ 翻他的 write_set 取旧版本；他 INSERT 的 → 我不可见
  4. 快路径：最新提交时间戳（acquire）≤ 我的 start_ts → 物理记录就是我的版本
  5. 慢路径：沿着写历史倒带，跳过所有比我 start_ts 新的提交，找到我该看的版本；倒带结果是空 → 不可见

2. 知道 unordered_map 为什么不能无锁并发读 ✅

答（见 6.5 节）：rehash 时旧桶数组被释放，读者持悬垂指针；桶链表在写操作中会被改指针，读者走到一半结构就变了；find 本身是"算哈希→找桶→走链表→比较"多步操作，不是原子的。结论：容器非线程安全，必须加锁或换并发容器。

3. 能说清 memory_order_acquire/release 的用途 ✅

答（见 6.3~6.4 节）：release/acquire 是一对"发布-订阅"。release store 保证它之前的所有写入在发布后对外可见；acquire load 保证读到该值后，能看到发布者 release 之前的所有写入。在 RMDB 里：提交事务先写完整写历史，再 release 发布 newest_committed_write_ts_；读者 acquire 读到时间戳比自己的 start_ts 大时，保证能看到完整的写历史，从而正确倒带版本。没有这对顺序保证，读者可能读到"时间戳新了但历史还没写全"的半成品状态。
