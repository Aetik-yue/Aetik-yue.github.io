阶段六：决赛冲刺清单（最后 1 周）

来源：数据库内核学习路线 阶段六
定位：对照赛题逐项自查。赛题 PDF（C:\Users\yanha\Desktop\ob2026\2026年全国大学生计算机系统能力大赛数据库系统设计赛-决赛赛题.pdf）是唯一权威规范，本清单是它的"复习提纲"。
前置：阶段五-动手实践（压测脚本 + 协议脚本必须已有）

一、最后一周的时间分配（7 天）

天 重点 动作
第 1 天 正确性 五类事务逐类过；NewOrder 回滚、Delivery 空队列专项测
第 2 天 隔离 48 个历史测试全绿；SI/SSI 语义专项（专项 4 脚本）
第 3 天 聚合 + FLOAT COUNT(DISTINCT) 两种写法；SUM(FLOAT) 双精度；±0
第 4 天 协议 协议脚本逐字节比对；AUTO_ABORT、BATCH_RESULT 状态码
第 5 天 持久化 + 恢复 崩溃恢复全套：kill -9 → 重启 → 数据完整 → <90s
第 6 天 性能 32 客户端 warmup 不崩；三类窗口 NewOrder 中位数优化
第 7 天 全量回归 + 备份 全套测试 + 比赛环境演练 + 代码备份

二、正确性清单

2.1 五类事务（TPC-C）

事务 验证点 容易错的地方
NewOrder 订单、订单行、库存数量都正确 10% 概率无效商品 → 整个事务回滚（不是部分回滚！）
Payment 客户余额累加正确 相对更新 c_balance = c_balance + ?（并发下不丢更新）
OrderStatus 返回最近订单状态 只读，快照内多次执行结果一致
Delivery 最旧未交付订单被交付 空队列跳过（不报错、不产生副作用）
StockLevel 库存低于阈值的商品数 范围查询走 B+ 树，结果精确

2.2 自测方法

三、隔离清单

3.1 三条铁律（对照代码位置）

  1. SI 快照可见性：读者只看自己 start_ts 之前已提交的版本 → GetVisibleRecord（transaction_manager.cpp:879）五步逻辑
  2. 写写冲突：同记录活跃写者冲突 → 等 200ms 超时 → ABORT → WaitWriteTurn（:620）
  3. SSI 立即中止：rw 边形成危险结构 → 立即 ABORT → AddRwEdgeAndCheckDangerous（:223）

3.2 48 个历史测试（决赛隔离分全部来源）

  • 跑法：./build/bin/unit_test（隔离测试全在里面）
  • 要求：一个都不能挂
  • 如果挂：先看挂的是 SI 还是 SSI 场景 → 对照上面三个函数排查
  • 并发挂掉第一反应：ASAN/TSAN 重编重跑，看是不是数据竞争（大概率是）

3.3 专项验证（用阶段五专项 4 的脚本）

  • 两个连接并发 UPDATE 同一行 → 第二个 ABORT
  • 快照内重复读 → 结果一致
  • 写偏斜场景（医生值班）→ SSI 下必有一个 ABORT

四、聚合清单

4.1 COUNT(DISTINCT) 两种括号写法

赛题考点：COUNT(DISTINCT col) 两种解析写法都要支持：

  • 标准写法：COUNT(DISTINCT col)
  • 可能的变体/别名写法（以赛题 PDF 为准）

4.2 join + 去重

SELECT COUNT(DISTINCT a.x) FROM a JOIN b ON ...——先 join 再去重，验证结果 = 手工 SQL 对照。

4.3 快速路径别破坏语义

aggregate_executor.h 的 stream_count_star / stream_index_count 快速路径（阶段四读过）——快速路径返回的结果必须和慢路径完全一致，特别是：

  • 空表 COUNT = 0
  • 有 NULL 时 COUNT(col) 不计 NULL（如果赛题有 NULL 语义）
  • 等值条件 + 索引计数的一致性（缓存失效是否正确）

五、FLOAT 清单（最容易丢分的细节）

5.1 三件事逐项过

考点 要求 验证方法
binary32 位模式 FLOAT 列按 IEEE 754 binary32 存盘/传输；比较按位模式 struct.pack('>f', x) 与服务器返回字节逐位比对
SUM(FLOAT) 双精度累加 累加过程用 double（binary64），不是 float 累加 手工 math.fsum 对照；大数+小数顺序测试（1e8 个 0.1 之类）
±0 归一 +0.0 与 -0.0 处理一致（位模式不同但数学相等） 构造 -0.0 用例，看输出/比较行为

5.2 常见翻车点

  • 用 float 累加 SUM → 精度漂移（累加 10 万次误差就出来了）
  • 相等比较用 == 而不是位模式比较 → 明明相等的值判不等
  • %f 打印舍入和赛题要求的输出格式不一致 → 输出格式以赛题为准

六、协议清单

6.1 帧格式（wire_protocol.h 已核实）

6.2 必须验证的场景

  • [ ] 握手：发 8 字节 → 收到正确响应（逐字节比对）
  • [ ] EXEC_STREAM：逐条 SQL 正常执行
  • [ ] PREPARE_SET + EXEC_BATCH：参数绑定正确（类型、长度、值）
  • [ ] AUTO_ABORT：事务出错时服务器的自动中止行为（错误后事务状态正确）
  • [ ] BATCH_RESULT 状态码：成功/失败的返回码符合赛题附件 A
  • [ ] 错误场景：非法 SQL、类型不匹配、事务中止 → 服务器不崩、返回正确错误码

6.3 验证工具

阶段五专项 1 的协议脚本 + strace -e trace=write,read -p <pid> 抓原始字节流核对。

七、持久化清单

7.1 三条铁律

  1. commit 前 fsync：提交时日志必须先刷盘（WAL 原则）——搜代码里 fsync 位置，确认 commit 路径有刷盘
  2. SIGKILL 后数据完整：kill -9 后重启，已提交数据一行不少、未提交数据全部消失
  3. 90 秒内恢复：大库崩溃后重启，到 show tables; 就绪 < 90s

7.2 完整恢复测试流程（每次改恢复代码都跑）

恢复慢的优化方向（如果 >90s）：

  • checkpoint 太旧 → analyze 从太早开始 → 调整 checkpoint 频率
  • redo 重放太多无用日志 → 看 analyze 的筛选逻辑
  • 参考 test_postcrash_consistency.py / repro_postcrash.py（仓库里已有恢复测试脚本）

八、性能清单

8.1 指标

指标 要求
32 客户端 warmup 不崩（warmup 阶段就要扛住）
NewOrder 延迟中位数 越低越好（主要指标）
三类窗口 赛题要求的三个时间窗口各自达标

8.2 压测流程

8.3 优化优先级（时间不够就按这个顺序）

  1. 确认快速路径在跑：rmdb.cpp 的快速 INSERT/COUNT 拦截是否命中（日志）
  2. 缓冲池不抖动：池大小够不够（页淘汰频率高不高）
  3. 锁粒度：热路径上有没有不必要的全局锁（分片锁用了没）
  4. 日志刷盘频率：commit 刷盘能不能批量/分组提交
  5. B+ 树：分裂频率、count_range 是否走快速路径

原则：先测量再优化——用压测脚本的延迟分布定位热点，不要凭感觉改。

九、决赛当天流程（演练一遍）

应急策略（记在脑子里）：

  • 测试中崩溃 → 先重启服务跑恢复验证，别慌着改代码
  • 挂掉的测试 → 记录复现命令，赛后 30 分钟冷静期再修
  • 一切以赛题 PDF 为准：有分歧时，赛题 > 本清单 > 代码注释

十、最终检查表（比赛前夜）

  • [ ] 代码已备份（git commit + 压缩包）
  • [ ] build-release 全新编译通过
  • [ ] unit_test 全绿（含 48 个隔离测试）
  • [ ] 五类事务手测通过
  • [ ] 崩溃恢复测试通过（数据完整 + <90s）
  • [ ] 协议脚本逐字节验证通过
  • [ ] 32 客户端压测：warmup 不崩、成功率 100%（SI 允许的 ABORT 除外）
  • [ ] FLOAT 三件事验证过（位模式/双精度/±0）
  • [ ] 比赛流程完整演练一遍
