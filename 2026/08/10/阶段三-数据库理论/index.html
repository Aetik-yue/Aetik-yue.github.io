二、磁盘与页管理

2.1 为什么数据库不直接读写文件字节？

假设一张表 100 万行。如果每次查一行都去磁盘读那一行的字节，磁盘寻道就慢死了。数据库的做法：按"页"为单位读写——一次读一整页（通常 4KB~8KB），页里塞很多行，用完留在内存缓存里（缓冲池，下一节）。

2.2 页（Page）是什么

定义：磁盘和内存之间传输的最小单位，固定大小（RMDB 是 4KB = PAGE_SIZE）。

看仓库 src/storage/page.h:66-68：

每页开头 4 字节存 LSN（这条修改对应日志的第几条），这是崩溃恢复时判断"这页要不要重做"的关键（阶段三第 10 节讲）。

Page 类（page.h:51）还有几个重要成员：

pin_count_ 是重点：页被某个线程"借用"时 pin 一下（+1），用完 unpin（-1）。pin > 0 的页不允许被踢出内存——否则你正读着，页被换走了，指针就悬空了。

2.3 表文件长什么样（堆文件组织）

三、缓冲池

3.1 问题：内存有限，数据无限

表可能有 10 万页，内存只能装 1000 页。用户访问哪页就加载哪页，装不下了必须淘汰一页。淘汰谁？——LRU：最近最少使用。

3.2 缓冲池的四个角色

访问流程（fetch_page）：

  1. 查页表：页在内存吗？在 → pin_count_++，直接返回（快，微秒级）
  2. 不在 → 问 replacer 要一个 victim 帧（LRU 选的）
  3. victim 是脏页？→ 先写回磁盘
  4. 从磁盘读目标页进这个帧，pin_count_ = 1，返回

3.3 并发细节（你已经会了）

阶段二精读过的 buffer_pool_manager.cpp：

  • latch_ 保护页表和帧状态
  • 锁外 I/O：磁盘读写放锁外（临时拷贝数据带出临界区）
  • loading_pages_ + loading_done_：同一页并发加载去重

3.4 淘汰策略

src/replacer/lru_replacer.h：

内部实现就是一个"最近使用链表"：被访问的帧移到链表头，victim 从链表尾选。这就是阶段五练习 1 要改的地方（加统计日志）。

四、B+ 树索引

4.1 为什么需要索引？为什么是 B+ 树不是哈希表？

  • 没有索引：查一行要全表扫描（读所有页）——慢
  • 哈希表：单点查询 O(1)，但范围查询（WHERE id BETWEEN 1 AND 100）要全表扫——哈希键值无序
  • B+ 树：单点查询 O(log n)，范围查询也快（叶子节点之间有链表，顺着走就行）——TPC-C 里全是范围查询（比如查最近 20 个订单），所以用 B+ 树

4.2 B+ 树长什么样（30 秒直觉版）

规则（只记核心）：

  1. 所有数据都在叶子节点（内部节点只存"路标"键值，帮你在树里找路）
  2. 叶子节点按顺序串成链表 → 范围查询 = 找到起点顺着链表走
  3. 节点满了 → 分裂成两个；删到太空 → 合并（或借一个）
  4. 平衡的：从根到任何叶子的距离一样

4.3 仓库实现

src/index/ix_index_handle.h：

亮点：WriterPreferredSharedMutex——普通 shared_mutex 有个问题：读者源源不断时写者会饿死（一直等）。B+ 树里写操作（分裂/合并）很关键，所以用"写者优先"的读写锁。这是阶段二"共享锁 vs 独占锁"知识的实战升级。

决赛性能点：aggregate_executor.h 里有个 count_range 快速路径（第 518 行 ih->count_range(begin, end)）——用 B+ 树直接数区间内有多少键，根本不扫数据。这就是 COUNT(*) WHERE id BETWEEN ... 快的原因。

五、火山模型（查询执行）

5.1 是什么

火山模型（Volcano Model）/ 迭代器模型：每个查询算子（扫描、过滤、连接、聚合）都是一个类，暴露统一的 Next() 接口——“给我下一行”。上层算子调用下层算子的 Next()，像流水线一样一行行"泵"上来。

为什么叫火山：数据像岩浆一样从底层算子（扫描）一层层喷到顶层（输出）。

5.2 仓库实现

src/execution/executor_abstract.h 你已经读过：

每个算子一个类，都继承它并实现 Next()：

执行器 文件 干什么
SeqScanExecutor executor_seq_scan.h 全表扫描（+ MVCC 可见性过滤，决赛重点）
IndexScanExecutor executor_index_scan.h 走 B+ 树找行
InsertExecutor executor_insert.h 插入（冲突检查 + WAL + 索引维护）
UpdateExecutor executor_update.h 更新（含相对更新 relative，TPC-C 用）
NestedLoopJoinExecutor executor_nestedloop_join.h 两重循环连接
AggregateExecutor aggregate_executor.h 聚合（SUM/COUNT/AVG…）+ 快速路径

5.3 例：SELECT * FROM t WHERE id > 5 怎么跑

每行数据从底往上"泵"：扫描器读一行 → 过滤器判断 → 通过就输出。整个查询只需要一张"下一行"的接口，这就是火山模型的可组合性——任意算子可以拼成任意查询计划。

六、查询优化

问题：SELECT ... FROM a, b WHERE a.id = b.id AND a.x > 10 有无数种执行方式：

  • 先过滤 a 再连接？还是先连接再过滤？
  • 用全表扫描还是索引扫描？
  • 谁做外表谁做内表？

优化器（src/optimizer/）负责把 AST 变成"最划算"的执行计划：把过滤条件下推（先缩小数据量再做贵操作）、决定扫描方式（有索引走索引）、选择连接顺序。

阶段四/五你只需要知道：RMDB 的优化器相对简单（规则优化为主），决赛的快速路径在 rmdb.cpp 里手工拦截常见 SQL（比如快速 INSERT 解析、COUNT 快速路径），不走完整优化流程——这是理解 rmdb.cpp 快速路径的钥匙。

七、事务与隔离级别

7.1 事务（Transaction）

定义：一组 SQL 的集合，要么全部成功，要么全部不执行（原子性）。

四大特性 ACID（背下来）：

特性 含义 违反的后果
Atomicity 原子性 全做或全不做 转账扣了钱但没到账
Consistency 一致性 事务前后数据都合法 余额变负数
Isolation 隔离性 并发事务互不干扰 读到别人改了一半的数据
Durability 持久性 提交了就永久保存 崩溃后数据丢了

7.2 并发会出什么问题（三种异常）

异常 场景 例子
脏读 读到别人未提交的修改 T1 改余额 100→90（没提交），T2 读到 90
不可重复读 同一事务两次读同一行，结果不同 T2 先读到 100，T1 改成 90 提交，T2 再读变 90
幻读 两次查询返回的行数不同 T2 第一次查到 5 行，T1 插入 1 行提交，T2 再查变 6 行

7.3 隔离级别（从松到严）

级别 防脏读 防不可重复读 防幻读
READ UNCOMMITTED ✗ ✗ ✗
READ COMMITTED ✓ ✗ ✗
REPEATABLE READ ✓ ✓ ✗（MVCC 下通常也防）
SNAPSHOT ISOLATION（快照隔离） ✓ ✓ ✓
SERIALIZABLE（可串行化） ✓ ✓ ✓（连写偏斜也防）

决赛只用两个：SNAPSHOT_ISOLATION 和 SERIALIZABLE（看 transaction_manager.cpp:592-594 的判断）。

关键区分（自测常考）：

  • SI 防幻读但防不了写偏斜（见第 9 节）
  • SSI（Serializable Snapshot Isolation） = SI + 检测读写冲突边，把"结果等价于串行执行"保证到底

7.4 仓库实现：Transaction 对象

src/transaction/transaction.h:58：

start_ts_ 是整个 MVCC 的基石：它既是"快照点"（我启动那一瞬间的数据库状态），又是"写者身份"（写写冲突时比大小）。

八、MVCC：多版本并发控制

8.1 核心思想：不互斥，改版本

传统的锁方案：读要锁、写要锁，读写互斥 → 并发度低。

MVCC（Multi-Version Concurrency Control）：同一行数据保留多个历史版本，读者读"自己快照时刻的版本"，写者写"新版本"，读写互不阻塞。

比喻：维基百科词条。你打开页面（快照）后别人怎么改都不影响你正在看的版本；你刷新（新快照）才看到新版。

8.2 快照隔离（SI）三句话

  1. 读：只读自己 start_ts 之前已提交的版本（GetVisibleRecord 干的活，阶段二已精读）
  2. 写：写之前检查"这行我启动之后有没有被别人写过"（写写冲突）
  3. 冲突就中止：SI 下写写冲突不等待、不覆盖，后到者直接 ABORT

8.3 写写冲突的判定（对应代码）

WaitWriteTurn（transaction_manager.cpp:620）+ CheckWriteConflict（:604）：

为什么"我启动后有提交"也算冲突：快照隔离要求我基于"启动时的旧数据"做修改，但别人已经把它改成新值了——我改下去会覆盖别人的提交（丢失更新）。所以必须中止。

8.4 版本从哪里来

RMDB 不把版本存在行旁边，而是存在写历史里：

  • write_history_ / write_history_by_key_：已提交事务的写入记录（AppliedWrite：旧值、新值、提交时间戳）
  • write_shards[128]：分片存储，每片一把锁（阶段二讲过）
  • GetVisibleRecord 的慢路径：沿着历史倒带，跳过所有比我新的提交，找到我该看的版本

删除怎么表示：INSERT_TUPLE 类型的写历史 + is_deleted_ 标记。倒带时遇到"我之后被插入"的行 → 我眼里它不存在（返回 nullptr）。

九、SSI：可串行化快照隔离

9.1 问题：SI 防不住写偏斜（Write Skew）

写偏斜经典例子（医生值班）：

诡异之处：两个事务写的是不同的行（a 行和 b 行），所以 SI 的写写冲突检测根本发现不了！但结果却不等价于任何串行顺序（先 T1 后 T2 或反之都不会出现 0 人值班）。

9.2 SSI 的解法：盯住"读写冲突"

关键观察：T1 读了 b 行（B 的值），T2 写了 b 行 → 存在 rw 边（T1 → T2）；T2 读了 a 行，T1 写了 a 行 → 存在 rw 边（T2 → T1）。两条 rw 边围成一个环 = 危险结构（dangerous structure） = 可能写偏斜。

规则：只要检测到"危险结构"，立即中止其中一个事务。

9.3 对应代码（逐行看）

transaction_manager.cpp:30：

加边 + 检查（第 223~234 行）：

危险结构检查（第 209~222 行 HasDangerousStructureAfterEdge）：新边 from → to 加入后，如果存在另一条边 x → from（且时间重叠）或 to → y（且时间重叠）——两条 rw 边首尾相接形成"读写交叉"——就返回 true → 调用方立即中止事务。

时间重叠判断（TxnIntervalsOverlap，第 197~207 行）：两个事务的 [start_ts, commit_ts] 区间有交集才算互相"看见"。这避免了误杀：一个已提交很久的事务留下的边不影响后来的事务。

触发点：RecordRead（第 707 行，记录"我读了哪行"）→ 后来者写同一行时 CheckSerializableWrite（第 795 行）检查所有读了我这行的活跃事务 → 形成危险结构 → 立即返回 true → 中止。

9.4 一句话总结 SSI

SI + 检测 rw 边环（危险结构）+ 发现即中止 = SSI。代码里 rw_edges_ 就是那个"环检测器"。

十、崩溃恢复：WAL 与 ARIES

10.1 问题：突然断电/被 kill -9，数据怎么办？

内存里缓冲池有脏页（改了没写盘）。崩溃后：

  • 已提交的事务可能没写盘 → 必须重做（redo），否则提交的数据丢了
  • 未提交的事务可能已经写盘 → 必须撤销（undo），否则半成品数据落库

问题：恢复时怎么知道哪个页的哪个修改是哪个事务的？——答案：日志（Log）。

10.2 WAL 原则：先写日志，再改数据

WAL（Write-Ahead Logging） 铁律：任何数据页的修改落盘之前，对应的日志必须先落盘。

为什么必须这样（自测第 3 题答案）：

  • 崩溃后，日志是唯一可信的记录——因为所有修改都有日志在先
  • 如果先改数据页再写日志：崩溃后日志里没有这次修改的记录 → 恢复时无法判断页上的数据是"已提交该留"还是"未提交该撤" → 数据处于未知状态
  • 先写日志保证：页上有的修改，日志里一定有 → 恢复时按日志重放即可，页状态完全由日志决定

10.3 日志长什么样（仓库代码）

src/recovery/log_manager.h:15-32：

prev_lsn_ 的意义：一个事务的多条日志串成链表，恢复时按事务为单位处理——从该事务最后一条日志沿 prev_lsn_ 往回走，就能撤销它做的所有修改。

子类：BeginLogRecord / CommitLogRecord / AbortLogRecord / InsertLogRecord / DeleteLogRecord / UpdateLogRecord（各自多带数据：插入的行、删除的旧值、更新的新旧值）。

事务对象里的对应物（transaction.h:89-93）：prev_lsn_ 和 has_begin_logged_——记录"我上一条日志在哪"和"我写过 BEGIN 日志没"。

10.4 ARIES 恢复三阶段（log_recovery.cpp）

恢复流程（RecoveryManager，src/recovery/log_recovery.cpp）：

① Analyze（分析）（第 110 行）——只读日志，不动数据：

  • 从哪开始读（checkpoint 记录的起点）
  • 找出哪些事务已提交（看到 COMMIT 日志）、哪些未完成（只有 BEGIN 没有 COMMIT）
  • 得出：该 redo 哪些（已提交的）、该 undo 哪些（未完成的）
  • 顺便重建缓冲池页表（哪些页在内存里）

② Redo（重做）（第 383 行，配合 apply_redo 第 336 行）——重放已提交事务的修改：

  • 从 analyze 给出的起点 LSN 开始，顺序扫日志
  • 对每条 UPDATE/INSERT/DELETE：如果属于已提交事务 → 重新应用
  • 幂等性关键：日志和数据页都有 LSN。重放时若页的 LSN ≥ 日志的 LSN → 这次修改已经生效，跳过（防止重复应用）
  • 注释原文（第 385 行）：“Redo committed changes in the physical order validated by analyze()”——按 analyze 验证过的物理顺序重放

③ Undo（撤销）（第 395 行）——回滚未完成事务：

  • 从最新的未完成事务开始，沿每条日志的 prev_lsn_ 往回走
  • 把修改恢复原状（UPDATE 恢复旧值、INSERT 删掉、DELETE 插回）
  • 每 undo 一条写一条 CLR（Compensation Log Record）——即使 undo 中途再崩溃，恢复也能接着撤（这个细节知道即可）

Checkpoint（检查点）（第 485 行 create_checkpoint，第 30 行 write_restart_file）——恢复加速器：

  • 恢复要从第一条日志扫起太慢。定期把"当前状态"存成 checkpoint
  • 崩溃后从最近的 checkpoint 开始恢复，不用重放全部历史
  • 代价：checkpoint 本身要写盘（慢），所以不会太频繁

10.5 为什么 redo 的日志顺序不能乱

两个事务可能交替写同一页的不同区域。redo 必须按日志物理顺序（LSN 顺序）重放——这就是为什么 analyze 要"验证物理顺序"，也是为什么 newest_committed_write_ts_ 的 release 发布顺序那么重要（阶段二）。

十一、TPC-C 负载

11.1 什么是 TPC-C

TPC-C 是一个模拟"商品批发商"的行业标准负载，测数据库在高并发交易下的性能和正确性。决赛就考它：32 个客户端并发跑五类事务，测正确性 + 延迟中位数。

11.2 五类事务（赛题第三章有精确 SQL，这里是语义）

事务 干什么 读的表 写的表 特点
NewOrder 新订单 客户下单（一次 1~15 件商品） warehouse, district, customer, stock, item order, order_line, stock 最复杂；10% 概率包含无效商品 → 整个事务回滚；更新库存数量
Payment 支付 客户付款 warehouse, district customer（余额累加） 更新 c_balance（相对更新：在旧值上加）
OrderStatus 订单状态 查客户最近订单的状态 customer, order, order_line 无 只读
Delivery 送货 每个 district 送一单最旧的未交付订单 order, order_line order, order_line, customer 队列空则跳过（不报错）
StockLevel 库存水平 统计最近 20 个订单涉及的库存中低于阈值的商品数 district, order_line, stock 无 只读 + 范围查询

11.3 和 RMDB 代码的对应

  • 相对更新：src/common/common.h:85-92 的 SetClause.relative——SET c_balance = c_balance + ? 这种"在旧值上累加"的更新，TPC-C 的 w_ytd/c_balance 全是这个模式。这是决赛正确性重点（并发下累加不能丢）
  • Delivery 空队列跳过：GetVisibleDeletedRecords（transaction_manager.cpp:950）——扫描时把"被删的行"也考虑进来，配合事务语义跳过空队列
  • StockLevel 范围查询：B+ 树的 count_range 快速路径（aggregate_executor.h:518）就是为这类查询准备的
  • NewOrder 回滚：写集合（write_set_）+ undo_logs_（transaction.h:160）——事务中止时把写过的全部撤销

11.4 决赛要关心的性能指标

  • NewOrder 延迟中位数：最主要指标
  • 三类窗口（赛题要求的三段时间窗口）
  • 32 客户端 warmup 不崩：并发稳定性

十三、自测清单（带答案）

1. 不看代码能画出 RMDB 架构图 ✅

2. SI 下两个事务同时 UPDATE 同一行会发生什么 ✅

答（对照 WaitWriteTurn）：

  1. T1 先到 → 登记 active_writers，开始写
  2. T2 想写同一行 → 发现活跃写者 T1 → 在 writer_released 条件变量上等最多 200ms
  3. 情况 A：T1 及时提交/中止 → T2 被唤醒 → 检查 latest_write_ts：T1 提交了 → 最新写时间戳 > T2 的 start_ts → 冲突，T2 中止（ABORT）；T1 中止了 → T2 可以写
  4. 情况 B：200ms 没等到 → T2 超时中止
  5. 结论：SI 下写写冲突，后到者必然中止（除非先到者回滚）。这就是"SI 功能模型要求同记录活跃写冲突以 TRANSACTION_ABORT 终止"（代码注释原话）

3. 解释"先写 WAL 再写数据页"为什么必要 ✅

答（见 10.2）：崩溃后日志是唯一可信来源。若先改数据页再写日志，崩溃后该修改"没有日志记录"，无法判断页上数据该留（已提交）还是该撤（未提交）——数据进入未知状态。WAL 保证：页上的任何修改，日志里必有对应记录，恢复时按日志重放（redo 已提交、undo 未提交）即可把数据库恢复到一致状态。这是 ARIES 能工作的前提。
