阶段五：动手实践（第 22~28 天）

来源：数据库内核学习路线 阶段五
目标：从"能读"到"能改"——每个任务都要编译 + 测试通过才叫完成。
前置：阶段四-RMDB代码精读
黄金法则：改任何代码前先跑一遍基线测试（./build/bin/unit_test），改完再跑一遍，用 ASAN 版再跑一遍。

一、7 个练习任务（难度递增）

任务 1：给 LRU 替换策略加统计日志（★，热身）

涉及：src/replacer/lru_replacer.h / .cpp

目标：统计并打印缓冲池的命中率（hit rate）：fetch_page 时页在内存 = 命中；不在 = 未命中。加一个计数器，每 1000 次访问打印一次。

怎么做：

  1. 在 LRUReplacer 或 BufferPoolManager 里加两个成员：hits_、misses_（size_t）
  2. fetch_page 命中/未命中的分支各 ++
  3. 每隔 N 次打印：hit rate = hits_ / (hits_ + misses_)

为什么做：热身 + 理解替换策略的调用点。做完你就能回答"什么时候会淘汰页"。

验证：跑一个 select * from 大表 的查询，日志里能看到命中率从低到高的变化。

任务 2：实现 SET enable_nestloop off 时退化为全表扫描 × 全表扫描的 join（★★）

涉及：src/execution/executor_nestedloop_join.h

目标：nested loop join 关闭时（设置项关闭），join 退化为"两个全表扫描笛卡尔积 + 过滤"——本质就是不用索引/不优化的暴力 join。

怎么做：

  1. 找到设置项 enable_nestloop 的读取位置（搜 enable_nestloop）
  2. 理解 NestedLoopJoinExecutor 现有实现：外层循环扫左表，内层循环扫右表，对每对行做连接条件判断
  3. 关闭时：确保左右子执行器都退化为 SeqScanExecutor（而不是 IndexScan），保持暴力双重循环语义

为什么做：理解"执行器树怎么组装"和"优化器开关怎么影响计划"。这是你第一次改执行逻辑。

验证：两个模式跑同一个 join 查询，结果集必须一致。

任务 3：给 SeqScan 加"每扫描 1000 行打印一次"的调试钩子（★★）

涉及：src/execution/executor_seq_scan.h（:191 附近的大 while 循环）

目标：扫描器每处理 1000 行，向日志打印一行 seq_scan progress: N rows。

怎么做：在 Next() 的循环里加一个计数器，count % 1000 == 0 时打印。注意：打印要轻量（别在热路径里做重活），这是以后你写调试钩子的模板。

为什么做：① 理解扫描器的逐行循环结构；② 以后查"扫描卡在哪"就用这种钩子。

验证：select * from 大表 能看到进度日志。

任务 4：实现 LIMIT 下推（★★★，端到端）

涉及：新建 executor_limit.h + planner（src/optimizer/）

目标：SELECT ... LIMIT 10 目前如果是在执行器树顶层过滤，扫描器会把所有行都扫出来再丢弃——浪费。下推 = 在扫描器/执行器链路上尽早停：扫到 10 行就停。

怎么做（从易到难选一个）：

  1. 简单版：新建 LimitExecutor，包装任意子执行器，Next() 只转发前 N 行，N 行后 is_end() 返回 true
  2. 下推版：把 LIMIT 信息传给 SeqScanExecutor，扫描器内部计数到 N 就提前结束扫描（真正"少扫"）

为什么做：这是你第一次新建执行器——完整走一遍"头文件 → 实现 → planner 挂接 → 编译 → 测试"的流程。决赛如果要加新功能（比如新的快速路径），就是这个流程。

验证：select * from 大表 limit 10 返回恰好 10 行；用 strace 或日志确认磁盘读取量变少（下推版）。

任务 5：给 AggregateCache 加 AVG 缓存（★★★）

涉及：src/system/sm_manager.h:35（AggregateCache）+ src/execution/aggregate_executor.h

目标：现有缓存（equality_counts，sm_manager.h:47）能缓存 COUNT(*) WHERE 等值条件 的结果。给同样的机制加 AVG 缓存。

怎么做：

  1. 读 AggregateCache 结构（:35-48）：equality_counts（等值条件 → 行数）怎么存、怎么失效（equality_counts_enabled 关闭机制）
  2. 理解 stream_count_star / stream_index_count（aggregate_executor.h:672/:444）怎么命中缓存
  3. 仿照加 equality_avgs（等值条件 → AVG 值）或类似结构
  4. 注意失效：任何写入（insert/update/delete）都要让缓存失效——找到现有失效点，AVG 缓存同样处理

为什么做：理解"缓存一致性"（写操作必须让缓存失效，否则读到旧值——这也是并发正确性问题），以及聚合快速路径的原理。

验证：同一查询跑两遍，第二遍走缓存（日志可见）；插入新数据后，查询结果必须变（缓存失效正确）。

任务 6：阅读题——CheckSerializableWrite 无锁访问 txn_map 的修复（★★★）

涉及：src/transaction/transaction_manager.cpp:795

背景：这个 BUG 已经修好了（仓库 commit 81590d8 附近的历史），现在的代码是正确的。你的任务是读懂修复后的代码，回答三个问题：

  1. 旧 BUG：CheckSerializableWrite 遍历 txn_map 时没拿锁，而其他线程同时在增删 txn_map（begin/commit/abort）→ 遍历时结构被改 → 崩溃/UB
  2. 现在怎么修的？（看 :795 附近的 txn_map_latch_ 加锁 + 双重检查 get_state() == GROWING）
  3. 为什么"遍历 txn_map 拿 map_lock 之后还要拿 other 的 write_set_latch_"？（防死锁顺序 + 防止读到 write_set 被并发改）

为什么做：这是"并发 BUG 长什么样、怎么修"的活教材。你在决赛现场遇到 SIGSEGV，大概率就是这种问题——先用 ASAN/TSAN 定位，再对照这个修复模式改。

验证：写 32 并发压测脚本（任务 7），开着 TSAN 跑 CheckSerializableWrite 相关路径，确认无 data race 报告。

任务 7：写 32 并发客户端压测脚本（★★★，决赛必备）

涉及：项目根目录，Python

目标：一个脚本，开 32 个线程（或进程）同时连数据库，每个客户端循环执行 TPC-C 风格操作（NewOrder 混 Payment…），统计成功率、延迟中位数、错误类型。

怎么做（两个层次）：

  1. 快速版：用 subprocess 调 rmdb_client 发 SQL（慢，但能用）
  2. 标准版：直接用 socket 实现 wire protocol（握手 → EXEC_STREAM → 逐条 SQL），参考 src/wire_protocol.cpp 和 rmdb_client 的代码。参考仓库里已有的 test_sim.py、quick_test.py

脚本骨架：

注意：帧协议细节（tag 字节、长度、参数编码）以赛题附件 A 和 wire_protocol.cpp 为准，先跑通单连接单语句，再扩并发。

为什么做：决赛 32 客户端压测就是它。warmup 不崩、中位数达标全靠这个脚本验证。

验证：32 客户端 × 100 次事务，成功率 100%（SI 语义下允许的 ABORT 除外），延迟中位数记录在案（作为优化前后对比基线）。

二、测试方法论（每次改代码的固定流程）

方法论要点：

  • 基线先行：改代码前先跑一遍测试，确认环境是绿的（否则你改完挂了分不清是不是你的锅）
  • 最小复现：出 bug 先写一个最小 SQL/脚本复现，再动手改
  • ASAN/TSAN 是安全网：内存/并发问题它们直接报行号，别用肉眼瞪代码
  • 回归意识：每个任务完成 = 全套测试过一遍

专项 2：FLOAT 语义测试

赛题考点（三件事）：

  1. binary32 位模式：FLOAT 列在磁盘上按 IEEE 754 binary32 存储。比较两个 FLOAT 相等 = 比较位模式（不是数学相等）
  2. SUM(FLOAT) 双精度累加：累加过程用 double（binary64）做，避免每加一次都舍入
  3. ±0 归一：+0.0 和 -0.0 位模式不同（符号位），但数学上相等——测试时要知道赛题要求归一成哪个

验证：struct.pack('>f', x) 对比服务器返回的字节；写 SELECT SUM(f) FROM t 用例，对照你手工用 Python math.fsum 或双精度累加算的结果。
