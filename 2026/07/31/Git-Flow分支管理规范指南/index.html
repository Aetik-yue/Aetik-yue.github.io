Git Flow 分支管理规范指南

在使用 Git 进行版本管理的过程中，如果没有清晰的流程和规划，每个人都提交一堆杂乱无章的 commit，项目很快就会变得难以协调和维护。Git 版本管理同样需要一个清晰的流程和规范，Vincent Driessen 为了解决这个问题提出了 A Successful Git Branching Model，也就是本文要介绍的 Git Flow 模型。

一、Git Flow 常用分支介绍

Git Flow 模型定义了五种核心分支，每种分支各司其职，共同构成完整的开发流程。

1.1 Production 分支（Master）

即我们经常使用的 Master 分支，这个分支保存的是最近发布到生产环境的代码。最近发布的 Release 都合并于此。

核心规则：

  • Master 分支只能从其他分支合并，不能在这个分支上直接修改
  • Master 分支上的每一个 Commit 都应该打上 Tag，标记版本号
  • 一般情况下 Master 分支本身不存在直接提交的 Commit

1.2 Develop 分支

主开发分支，包含所有要发布到下一个 Release 的代码。

核心规则：

  • Develop 分支基于 Master 分支创建
  • 该分支主要用来合并其他分支（如 Feature 分支）
  • 是日常开发的基础分支

1.3 Feature 分支

用于开发新功能的分支。

核心规则：

  • 基于 Develop 分支创建
  • 分支命名通常为 feature/功能名 或 feature-功能名
  • 开发完成后，合并回 Develop 分支
  • 合并完成后删除该 Feature 分支（保留下来意义不大）

1.4 Release 分支

当需要发布新版本时创建的分支。

核心规则：

  • 基于 Develop 分支创建
  • 分支命名通常为 release-版本号（如 release-0.1.0）
  • 在此分支上可以进行测试、Bug 修复等工作
  • 注意： 一旦打了 Release 分支之后，不要从 Develop 分支上合并新的改动到 Release 分支
  • 发布完成后，合并到 Master 和 Develop 两个分支
  • 在 Master 分支上打上 Tag 标记版本号
  • 删除 Release 分支

1.5 Hotfix 分支

用于紧急修复生产环境 Bug 的分支。

核心规则：

  • 基于 Master 分支创建（因为要修复的是生产环境问题）
  • 分支命名通常为 hotfix-版本号（如 hotfix-0.1.1）
  • 修复完成后，合并回 Master 和 Develop 两个分支
  • 在 Master 分支上打上 Tag 标记版本号
  • 删除 Hotfix 分支
  • Hotfix 的改动会进入下一个 Release

二、Git Flow 各分支操作流程

2.1 Master / Develop 分支关系

  • Develop 分支基于 Master 分支创建
  • 所有在 Master 分支上的 Commit 应该打上 Tag
  • Master 作为稳定的生产代码基线

2.2 Feature 分支流程

  • Feature 分支做完后，必须合并回 Develop 分支
  • 推荐使用 --no-ff 方式合并，保留分支的 commit 历史
  • 合并完分支后删除 Feature 分支

2.3 Release 分支流程

  • Release 分支基于 Develop 创建
  • 在此分支上测试、修复 Bug
  • 发布时同时合并到 Master 和 Develop
  • 在 Master 上打 Tag 标记版本号

2.4 Hotfix 分支流程

  • Hotfix 分支基于 Master 创建
  • 修复完成后同时合并回 Master 和 Develop
  • 在 Master 上打 Tag 标记版本号

四、分支命名规范建议

分支类型 命名格式 示例

五、总结

Git Flow 模型通过严格的分支定义和合并规则，为团队协作开发提供了清晰的流程规范：

  1. Master 分支始终保持生产环境可部署状态
  2. Develop 分支作为日常开发的主线
  3. Feature 分支隔离新功能开发，互不干扰
  4. Release 分支保障版本发布的稳定性
  5. Hotfix 分支快速响应生产环境问题

遵循 Git Flow 规范，可以让项目的版本管理更加有序，降低多人协作的复杂度，是每个开发团队都应该掌握的最佳实践。
